# منشور مهندسی و قوانین پایه پلتفرم سنترا (`docs/RULES.md`)

این مستند **منبع حقیقت (Single Source of Truth)** برای تمامی تصمیمات معماری، استانداردهای کدنویسی و الگوهای طراحی در مخزن `sentra-platform` است. کلیه مشارکت‌کنندگان، مهندسان و عوامل هوش مصنوعی موظف به رعایت بدون قید و شرط این اصول هستند.

---

## ۱. اصول معماری ماژولار در اکوسیستم Rust

پروژه «سنترا» بر پایه یک ساختار **Monorepo** چندکرِیتی (Multi-Crate Cargo Workspace) با مرزبندی‌های کاملاً ایزوله بنا شده است:

```text
sentra-platform/
├── Cargo.toml                         # ریشه ورک‌اسپیس و تعاریف وابستگی‌های مشترک
├── crates/
│   ├── sentra-core/                   # هسته بک‌اند: وب سرور Axum، منطق بیزینس، دیتابیس
│   ├── sentra-bot/                    # دیمن ربات تلگرام مبتنی بر teloxide (جدا از هسته)
│   ├── sentra-client/                 # لایه کلاینت Tauri v2 و کدهای نیتیو دسکتاپ/اندروید
│   ├── sentra-proto/                  # تایپ‌ها، DTOها، قراردادهای اشتراکی و ابزارهای رمزنگاری
│   └── sentra-sidecar/                # کنترل‌کننده پروسس‌های فرزند (Sing-box Engine Manager)
└── docs/                              # مستندات و قراردادهای معماری
```

### مرزبندی وابستگی‌ها (Layer Separation Invariants)
1. **استقلال هسته (`sentra-core`) از ربات و کلاینت:** هسته به هیچ‌وجه نباید وابستگی مستقیم به کدهای UI یا کتابخانه‌های تلگرام داشته باشد. تعامل ربات با هسته یا از طریق فراخوانی سرویس‌های مستقیم ماژولار است یا از طریق REST API داخلی.
2. **جداسازی کامل مدیریت پروسس شبکه (`sentra-sidecar`):** کنترل چرخه حیات `sing-box` (شروع، خاتمه امن، نظارت بر لاگ‌ها) باید در یک ماژول ایزوله قرار گیرد تا خطاهای پروسس فرزند هرگز باعث کرش کردن محیط Tauri یا رابط کاربری نشوند.
3. **عدم وابستگی به کدهای پلتفرم خاص در هسته:** کدهای مربوط به Windows TUN (مانند Wintun.dll)، لینوکس (`/dev/net/tun`) و اندروید (`VpnService`) باید به طور اکید در مرزهای کلاینت ایزوله بمانند.

## ۲. استانداردهای زبان Rust و تاب‌آوری کدهای تولیدی

### الف) قانون صفر آن‌رپ («Zero Unwraps» in Production)
- استفاده از `.unwrap()`، `.expect()`، `panic!()` و `unreachable!()` در سراسر کدهای تولیدی (`src/`) **مطلقا ممنوع** است.
- خطاها پدیده‌های طبیعی شبکه هستند (قطعی DNS، مسدودسازی TLS، تایم‌اوت سوکت) و باید به شکل ساختاریافته کنترل شوند.
- تنها استثنا: بلوک‌های تستی (`#[cfg(test)]`) جهت اعتبارسنجی فرضیات تست.

### ب) معماری یکپارچه مدیریت خطا (Hierarchical Error Handling)
1. **خطاهای دامنه‌ای (Domain Errors) با `thiserror`:** تمام پکیج‌های کتابخانه‌ای و سرویس‌های داخلی باید انواع خطاهای Strongly Typed خود را با `thiserror` تعریف کنند:
   ```rust
   use thiserror::Error;

   #[derive(Error, Debug)]
   pub enum CoreError {
       #[error("دیتابیس در دسترس نیست: {0}")]
       Database(#[from] sqlx::Error),

       #[error("نشست کاربری نامعتبر است یا منقضی شده")]
       InvalidSession,

       #[error("سقف حجم اشتراک {tier} به پایان رسیده است")]
       QuotaExceeded { tier: String },

       #[error("خطای ارتباط با زیرسیستم شبکه: {0}")]
       Network(String),
   }
   ```
2. **مرزهای اپلیکیشن با `anyhow`:** در لایه هندلرهای وب (Axum Handlers) و فرامین IPC در Tauri، خطاها با لایه‌های متنی واضح بسته‌بندی می‌شوند:
   ```rust
   use anyhow::Context;

   pub async fn start_proxy_subsystem() -> anyhow::Result<()> {
       prepare_wintun_driver()
           .await
           .context("بارگذاری درایور کارت شبکه Wintun با شکست مواجه شد")?;
       Ok(())
   }
   ```

### ج) مدیریت حافظه، تسک‌های ناهمگام و انصراف تمیز (Graceful Cancellation)
- تمام تسک‌های پس‌زمینه با `tokio::spawn` باید مجهز به توکن انصراف (`tokio_util::sync::CancellationToken`) باشند تا در صورت خروج کاربر یا بستن اپ، بدون نشت حافظه (Memory Leak) یا جا ماندن پروسس شبح (Orphan Process) بسته شوند.
- برای مانیتورینگ بلادرنگ سرعت و وضعیت اتصال، از کانال‌های دارای سقف (`tokio::sync::mpsc::channel(buffer)`) استفاده شود. کانال‌های بدون سقف (`unbounded`) به دلیل خطر سرریز حافظه در زمان فشار شبکه ممنوع هستند.

## ۳. الزامات انحصاری اسکیماهای Sing-box v1.10+

کلیه پیکربندی‌های تولیدشده توسط پلتفرم سنترا باید منطبق بر استانداردهای نگارش v1.10 به بعد باشند. استفاده از کلیدهای قدیمی ممنوع است:

| کلید / رفتار ممنوع (Deprecated / Legacy) | الزام معماری سنترا (Sing-box v1.10+) | علت و پیامد امنیتی |
| :--- | :--- | :--- |
| `domain_strategy` داخل قوانین مسیر | `rule_set` یا `domain_suffix` همراه با DNS پیشرفته | جلوگیری از تداخل مسیرهای DNS با تانل سیستم |
| استفاده از Inboundهای چندگانه متفرقه | استفاده متمرکز از `type: "tun"` با استک `mixed` | تضمین عملکرد پایدار بدون نشت DNS در ویندوز/اندروید |
| آدرس‌دهی دستی به رنج‌های لوکال | `fakeip.inet4_range: "198.18.0.0/15"` | پنهان‌سازی واقعی نام دامنه‌ها از بازرسی عمیق پاکت (DPI) |
| استفاده از تگ‌های غیرشفاف | تگ‌های رسمی: `Sentra Auto`, `Sentra Hydra`, ... | تطابق کامل با منطق سوییچ خودکار و انتخاب دستی کاربر |

## ۴. استانداردهای زبان فارسی و طراحی رابط کاربری (Tauri v2 UI/UX)

رابط کاربری کلاینت «سنترا کانکت» برای میلیون‌ها کاربر با سطوح مهارتی گوناگون طراحی می‌شود. هرگونه پیچیدگی بیهوده حذف می‌گردد.

### الف) راست‌چین اصیل (RTL-First Architecture)
- ریشه رابط کاربری دارای ویژگی `dir="rtl"` و `lang="fa"` است.
- جهت‌گیری عناصر (پدینگ‌ها، مارجین‌ها، پاپ‌آپ‌ها و دکمه بازگشت) باید به درستی معکوس شوند (`start` / `end` به جای `left` / `right` در CSS).
- فونت استاندارد برنامه: خانواده **وزیرمتن (Vazirmatn)** به صورت محلی و Embed شده در کلاینت برای اطمینان از نمایش عالی حتی در صورت قطعی اینترنت.
- اعداد انگلیسی و ارقام فنی (مانند `42.5 MB/s` یا پینگ `120ms`) باید با فونت‌های مونو یا حالت `tabular-nums` نمایش داده شوند تا از پرش کاراکترها جلوگیری شود.

### ب) پرهیز مطلق از کلیشه‌های طراحی مصنوعی (Anti-AI Clichés)
- **ممنوع:** گرادینت‌های رنگین‌کمانی تکراری، حاشیه‌های نئونی درخشان فانتزی، پس‌زمینه‌های فضایی شلوغ، لودرهای بیش از حد متحرک که به کاربر حس ناامنی می‌دهند.
- **الزام:** طراحی مینیمال، ابزارمحور (Utility-First)، الهام گرفته از نرم‌افزارهای امنیتی روز دنیا (مانند 1Password، ProtonVPN، Windscribe).
- **پالت رنگی:** استفاده از تم تیره عمیق (Deep Slate/Zinc) با لهجه‌های کاربردی (سبز زمردی برای وضعیت متصل، کهربایی برای در حال اتصال، قرمز مات برای خطا).
- **طراحی برای تمام سنین:** کلید بزرگ اتصال یک‌کلیکی (Single Large Connect Button) در مرکز صفحه؛ کاربر بدون نیاز به دانش شبکه باید بتواند در کمتر از ۲ ثانیه اتصال خود را برقرار کند.

## ۵. استراتژی توسعه ایزوله و تست بدون هزینه (Zero-Cost Sandbox)

- در فاز اول توسعه، **هیچگونه هزینه خرید سرور، VPS یا دامنه خارجی نباید تحمیل شود**.
- تمامی خروجی‌ها (Outbounds) در تست‌های لوکال به پورت‌های محلی Loopback (`127.0.0.1:10801-10804`) متصل می‌شوند.
- درایور TUN در حالت تست با ارسال بسته‌ها به سرویس‌های تست داخلی بدون ایجاد اختلال در ترافیک اصلی سیستم‌عامل کاربر عمل می‌کند.
- تمام تراکنش‌های ارتقا در ربات تلگرام در فاز یک به درگاه‌های پرداخت متصل نیستند و از دکمه شبیه‌ساز پرداخت تلگرام (`Mock Payment Gateway Simulator`) استفاده می‌کنند.
